# 个人网站开发计划

本文档基于 [个人网站功能列表_prd.md](./个人网站功能列表_prd.md) 整理，约定**单页滚动**首版交付范围（PRD 第七章「第二阶段」功能默认不包含，除非另行确认）。

---

## 一、模块拆分

| 编号 | 模块名称 | 对应 PRD |
|------|----------|-----------|
| M0 | 工程与设计基础 | 技术栈、UI 与动效总规范、整体信息架构骨架 |
| M1 | Hero 首屏 | §1 Hero |
| M2 | 项目展示（核心预览） | §2 三项目 Case Study 风格展示 |
| M3 | Case Study 深度内容 | §3 统一叙事结构 |
| M4 | 技能模块 | §4 Skills |
| M5 | 关于我 | §5 About |
| M6 | 联系方式 | §6 Contact |
| M7 | 动效整合、性能与发布 | §五 动效规范、§六 部署；工具链收口 |

说明：**M2 与 M3** 在页面上为先后区块（Hero → Projects → Case Study）。M2 侧重「看什么、亮点有哪些」；M3 侧重「问题—目标—设计—AI—思考—取舍—结果」完整链条。

## 二、各模块职责

### M0 工程与设计基础

- Next.js + Tailwind 工程与目录约定。
- 全局视觉基底：浅色极简、大留白、杂志感排版（字体、间距、颜色、容器最大宽度）。
- 单页骨架：区块 `id`、锚点导航（桌面 + **移动端友好**方案，例如顶栏 + 抽屉/简化导航，实现阶段再定）。
- 可复用布局：Section 容器、标题层级、响应式断点策略。
- 内容与资产前置确认：项目截图/配图、简历文件、联系方式、微信展示方式、项目结果/现状文案，避免进入页面实现后反复返工。

### M1 Hero 首屏

- 姓名、「AI Product Builder」定位、简介（含 B 端年限、AI 落地方向等 PRD 要点）。
- CTA：查看作品、联系我；（可选）下载简历。
- 为首屏动态背景与微动效预留接入点；具体动效在 M7 统一收敛。

### M2 项目展示

- 三个项目：**自然拼读英语**、**英语小故事**、**CRM AI**。
- **Case Study 气质**：每块含短叙事 + 关键能力/亮点 + 适配图（素材未齐时可用占位与固定文案结构）。
- 与 M3 使用同一份 `projects` 数据源，项目名称、定位、亮点、事实描述保持一致。
- 移动端纵向堆叠，触控区域与字号达标。

### M3 Case Study 深度模块

- 按 PRD **3.1～3.7** 组织内容：用户问题、产品目标、核心设计、AI 参与方式、产品思考、MVP 取舍、项目结果。
- 必须与 M2 共用同一份「项目」数据源，避免重复维护与文案冲突。
- 移动端：分段清晰（小标题、列表、留白）；必要时用折叠/子锚点（实现阶段再定），避免「一屏满字墙」。
- 首版 Case Study 以「精简但完整」为原则：每个项目覆盖统一结构，但避免写成独立详情页级别的长文。

### M4 技能模块

- 四类：**AI / 产品 / 数据 / 技术协作**，与 PRD 列举项对齐。

### M5 关于我

- 个人经历路径、当前关注方向、产品理念，与整站定位一致。

### M6 联系方式

- 邮箱、微信；GitHub / 小红书 / 即刻等按 PRD 选填。
- 注意隐私与反爬：微信展示方式（二维码、引导文案、复制按钮等）需在实现前确认，避免影响 UI 与交互。

### M7 动效整合、性能与发布

- Unicorn Studio（Hero 背景）、Framer Motion、React Bits（Reveal、Hover、按钮等），遵守「微动效、克制、慢节奏」。
- 首版动效优先级：Framer Motion + CSS/Tailwind 微动效为必做；Unicorn Studio 作为 Hero 背景增强；React Bits 仅在组件确实合适时引入，避免工具链过重。
- 移动端与弱网：`prefers-reduced-motion`、背景/动效降级策略。
- Vercel 发布；基础 `title` / `description`（OG 图可后续补）。

## 三、开发顺序与依赖关系

| 顺序 | 模块 | 原因与依赖 |
|------|------|------------|
| 1 | M0 | 无内容依赖；先定骨架、设计令牌与导航，后续模块才有一致容器。 |
| 2 | M1 | 依赖 M0；首屏定调，CTA 依赖锚点与 section `id`（M0）。 |
| 3 | M2 | 依赖 M0；核心案例区，优先保证「三项目」在滚动叙事中立住。 |
| 4 | M3 | 依赖 M0 + **必须与 M2 共用项目数据模型**；在 M2 结构稳定后展开长叙事，减少返工。 |
| 5 | M4 → M5 → M6 | 依赖 M0；内容独立、改动面小，放在案例之后填充。 |
| 6 | M7 | 依赖 M1～M6 **版式与文案基本稳定**；动效与第三方背景对性能影响大，最后收口。 |

**显式依赖小结**

- 所有内容模块依赖 **M0**（布局、导航、锚点）。
- **M2/M3 依赖统一项目数据模型**（同一批项目、同一套事实描述、同一组项目定位），应在实现 M2 前先确定 `projects` 数据结构。
- **M7 依赖内容区块定型**，否则动效与背景要反复调整。
- **M6 依赖联系方式与隐私策略确认**，尤其微信展示方式会影响 UI 形态。

**PRD 第二阶段**（Blog、独立项目详情页、多语言、CMS）不纳入本顺序，除非单独排期。

## 四、验收标准

### M0

- 工程可本地构建运行，`npm run build` 通过；页面无明显控制台错误。
- 单页各区块具备稳定 `id`，导航/CTA 能跳到对应 section。
- 至少验收 375px、768px、1440px 三类视口；无横向滚动溢出，正文与可点击区域尺寸合理。
- 样式以设计令牌/组件复用为主，避免大量一次性 magic number。
- 项目素材、简历文件、联系方式等缺失项有明确占位策略或待确认清单。

### M1

- 首屏在 30 秒内能传达：**姓名 / AI Product Builder 定位 / 8 年 B 端经验 / AI 产品落地方向 / 核心能力关键词**。
- CTA 行为与整站约定一致（如「查看作品」到 Projects、「联系我」到 Contact；若提供简历，下载链接可用）。
- 移动端首屏信息层级清晰，关键文案不被导航或安全区遮挡。

### M2

- 三项目均有独立呈现，且每块至少包含：项目定位、短叙事、关键能力/亮点、展示素材或明确占位。
- 三个项目分别体现 PRD 要求的能力与亮点维度；呈现为 Case Study 风格，而非纯截图堆叠。
- 移动端浏览与点击顺畅，卡片/链接触控区域可用，无内容挤压或遮挡。

### M3

- 每项目（或你确认的合并方式）覆盖 **3.1～3.7** 结构类型，无整套段落缺失；与 M2 事实、项目定位、能力描述不矛盾。
- 每个项目至少覆盖：用户问题、产品目标、核心设计、AI 参与方式、产品思考、MVP 取舍、项目结果/当前状态。
- 移动端可扫读（标题、列表、间距），避免连续大段文字堆叠。

### M4

- 四类技能及 PRD 子项有对应展示；移动端无严重换行/溢出。

### M5

- 经历、关注方向、理念三块齐全，与「AI Product Builder」定位一致。

### M6

- 必备渠道可用：邮箱可点击或可复制；微信按确认方案展示。
- 可选渠道与 PRD 一致或明确标注未提供；前台不暴露不必要隐私。

### M7

- Hero 背景与全页动效符合「柔和、克制」；支持 `prefers-reduced-motion` 时减弱或关闭非必要动画。
- 移动端首屏与滚动过程无明显卡顿、大幅 CLS、内容跳动或动画遮挡。
- 至少完成一次桌面与移动端浏览检查；如需要硬指标，可在进入 M7 时补充 Lighthouse / LCP / CLS 目标。
- Vercel 生产环境可访问；基础元信息可被抓取（后续可再增强 OG）。

## 五、规划自检（模块 / 顺序 / 验收 / 范围）

### 模块是否合理、有无遗漏

- **合理**：与 PRD 单页结构（Hero → Projects → Case Study → Skills → About → Contact）一一对应；M0/M7 覆盖「骨架 + 收口」工程现实。
- **可选补强（非必须单独成模块）**：若首版要强 SEO，可在 M0/M7 增加 **sitemap、结构化数据、社交分享图** 等条款；PRD 未强制，可按上线需求追加。
- **内容资产**：图片/视频/简历文件、项目结果/当前状态、联系方式若由你提供，计划中不单独设模块，但已在 M0 作为前置确认项；**M1（简历）与 M2/M3（配图）** 会受素材到位情况影响排期。

### 顺序与依赖是否考虑充分

- **顺序总体正确**：先骨架与首屏定调，再核心案例，再浅层信息区，最后动效与发布。
- **关键依赖**：M2 与 M3 的**数据与叙事一致性**必须在实现上绑定（必须共享项目数据源），否则易出现维护与文案冲突。
- **前置确认**：项目数据模型、素材策略、联系方式隐私策略建议在 M2/M6 实现前确认。

### 验收标准是否够具体

- 当前标准以**可观察行为与体验**为主（构建通过、锚点、无溢出、结构完整、动效原则、发布可用）。
- **偏定量的指标**（具体 LCP 毫秒、Lighthouse 分数）未写死，避免脱离真实素材与托管环境空谈；若你需要硬指标，在启动 M7 前补充一行即可。

### 是否过度复杂

- **未把第二阶段写进必做**：Blog、CMS、多语言、独立详情页均排除在默认范围外，避免首版膨胀。
- **M2 + M3 分两块** 是 PRD 本身结构所致；首版建议保留两块，但 M3 采用「精简 Case Study」，不写成独立详情页级长文。若你希望**极简首版**，可合并为「每项目一段长内容」并削减 M2 独立区块——属于产品取舍，需你确认。
- **Unicorn Studio + React Bits + Framer Motion** 为 PRD 点名工具，但首版不必全部强上；优先 **Framer Motion + 轻量 CSS/Tailwind 微动效**，Unicorn Studio 和 React Bits 按实际效果后补。

## 六、文档维护

- PRD 变更时，同步更新本计划的模块说明与验收标准。
- 若采用「项目独立路由」替代纯单页 Case Study 长区，在本文「模块拆分」与「顺序」中修订 M2/M3 描述即可。
