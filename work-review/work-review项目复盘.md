## 二、问题清单（本次做得不好的地方）

### 🔴 P0 — 根本性问题

#### 1. 数据模型没有在立项时设计清楚

`work_records` 里同时存在 `title`（快捷展示字段）和 `projects[].project_name`（结构化数据），导致：

- 两个字段语义重叠，可以独立更新，产生分裂
- 首页读 `title`，日报读 `projects[].project_name`，用户看到的和报告里的内容不一致
- 消耗了大量联调和排查时间（整个"工信部"迷局）

**根因：没有做数据字典 / 字段规范，边开发边往 DB 里加字段。**

#### 2. "ai-confirm 页"的职责边界模糊

该页面最初设计为"AI 整理结果确认 + 直接生成日报"的二合一入口，导致：

- 按钮文案"确认生成日报"让用户误以为保存 = 生成报告
- 导航栈混乱：`首页 → ai确认 → 日报 → 回退到ai确认`
- 多次补丁：加 `wx.redirectTo`、改 `wx.switchTab`、拆分"保存记录"和"生成日报"
- 每次新增功能都需要重新梳理这条链路

**根因：没有明确定义"录入"和"报告"是两个独立阶段。**

---

### 🟠 P1 — 流程设计问题

#### 3. 用户流程图（User Flow）缺失

整个项目从未画过一张完整的页面流程图，导致：

- 导航路径（navigateTo / redirectTo / switchTab）多次返工
- "查看已有日报"误触发"重新生成"（hasTodayReport 逻辑修了两遍）
- 期间报告（周报/月报）的查看 vs 生成 vs 重新生成三态，直到后期才稳定

#### 4. AI 行为没有提前约束

`createReport` 云函数的 Prompt 没有限制 AI 对项目名的处理权限，AI 会根据 actions 内容"优化重命名"项目名（把"今天忙啥了"改成"工信部评审准备与产品测试"），导致：

- 用户在 ai-confirm 修改了项目名，报告里依然显示 AI 自己起的名字
- 排查过程耗费大量时间，最后发现是 Prompt 工程问题

**根因：AI 模块没有"输入约束文档"，Prompt 只写了格式要求，没写禁止项。**

#### 5. 时区问题未在设计阶段解决

所有日期计算使用 `new Date().toISOString().slice(0, 10)`（UTC），在中国（UTC+8）凌晨 0:00–8:00 时会比本地日期少一天，可能导致：

- 当天凌晨录入的记录被归到"昨天"
- 本地日期和云端记录日期不一致

**现状：未修复，存在潜在 Bug。**

### 🟡 P2 — 工程实践问题

#### 6. 数据库字段随需求演进无规划叠加

| 字段 | 问题 |
|---|---|
| `actionsText` / `problemsText` / `hasProblems` | UI 计算字段存入 DB，不属于数据层 |
| `updateTime` | 本次才补加，早期编辑记录无法被"有新数据"检测识别 |
| `isDeleted` | 部分老文档无此字段，导致查询 `isDeleted: false` 时遗漏文档 |

#### 7. 周报 / 月报云端持久化是后补的

初版周报/月报只存 localStorage，换设备或清缓存后消失，需要补做 `savePeriodReport` / `getPeriodReport` 两个云函数。这是需求分析阶段应该明确的"多设备"场景。

#### 8. 没有可复用的测试数据集

整个开发过程中测试数据是随手录的，导致：

- "工信部评审准备"这类测试数据残留在 DB，干扰真实数据判断
- 无法区分"功能失常"还是"数据污染"
- 排查问题时经常花大量时间重建现场

## 三、下一次要怎么做

### 阶段 0：立项时（动第一行代码前）

| 产出物 | 说明 |
|---|---|
| **数据字典** | 每个 Collection 的字段名、类型、语义、更新时机，明确哪些是 DB 字段、哪些是 UI 计算字段 |
| **用户流程图** | 完整的页面跳转图，标注每个节点用 navigateTo / redirectTo / switchTab，以及返回后的预期状态 |
| **AI 模块约束文档** | 每个 AI 调用：输入格式、输出格式、禁止项（如禁止重命名用户设定的字段） |
| **跨端场景清单** | 多设备、清缓存、断网等场景，哪些数据需要云端持久化 |

### 阶段 1：设计时

- 每个页面只有一个明确职责（单一职责原则）
  - ai-confirm = 保存记录，不生成报告
  - report = 读取记录并生成/展示报告
- 明确"状态机"：每个页面有哪些状态（loading / error / 空 / 有数据），每种状态下展示什么、按钮是什么
- 时区统一采用**设备本地时间**（不用 ISO UTC），用 `${d.getFullYear()}-${m}-${day}` 格式

### 阶段 2：开发时

- **先做 Happy Path，再做异常**：把核心链路（录入 → 保存 → 首页 → 生成日报 → 查看）完整跑通，再加编辑、删除、周报等功能
- **测试数据隔离**：建一套固定测试账号和标准数据集，避免脏数据混入真实流程
- **DB 变更走版本记录**：新增字段时同步更新 CLAUDE.md 的字段文档，并确认历史文档的兼容性

### 阶段 3：验收时

- 每个功能点对照 User Flow 逐条验收，不只是"感觉没问题"
- 专门测试"数据一致性"：UI 展示的内容 = DB 存的内容 = AI 用来生成报告的内容，三者一致

## 四、核心教训（三条）

> **1. 数据模型决定一切**  
> 字段设计不清楚，后面的每个功能都是在还债。宁可设计阶段多花 2 小时，不要开发阶段花 2 天排查"为什么首页和日报显示不一样"。

> **2. 职责不清的页面是 Bug 温床**  
> "ai-confirm 既保存又生成报告"这一个决策，带来了至少 5 个需要单独修复的 Bug。产品设计时每个页面的进入条件、退出路径、数据写入时机必须明确。

> **3. AI 需要被约束，不能只被信任**  
> AI 是工具，它会"聪明地"做你没要求它做的事（比如重命名项目）。每个 AI 调用都需要明确的"禁止项"，和不依赖 AI 判断的字段（如用户自定义名称）要在 Prompt 里做硬性保护。
