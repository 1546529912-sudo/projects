基本功

让任何图都好看的设计原则

好看 = 克制 + 对齐 + 留白，不是加装饰。

下面是同一个流程（提需求 → 评审 → 上线）的两种画法。左边「随手画」，右边只是套了几条规则——内容没变，专业度天差地别。九成的丑图，是因为东西太多、太花、没对齐。

六条通用规则

① 对齐：所有元素卡在同一条隐形网格线上，这是业余感的头号来源。
② 配色克制：全图最多 2–3 色，且颜色代表含义（状态 / 分类），不为好看而上色。
③ 一致性：同类元素长一样——等宽等高、圆角统一、箭头统一。
④ 间距统一：留白相等、舍得留白，挤是第二大业余感来源。
⑤ 视觉层级：重要的更大、更重、更突出，眼睛知道先看哪。
⑥ 少交叉走直线：连线尽量横平竖直，宁可绕路也别穿过别的框。

一句话心法：先想清楚结构（发散 → 收敛），再用对齐、留白、克制配色把它画出来，复杂了就拆成多张图。工具只是执行这套规则的手。
思考发散

思维导图

回答：「关于这件事，有哪些想法？」

是什么

一个中心主题向外发散出主干和细枝，用来穷举和归类想法。它的本质是先发散、再收敛：先把想到的全列出来（别评判），再归类成几条大主干、去重、排序。

三条让它好看的规则：主干控制在 4–7 条（米勒定律）；颜色按主干分组，同一枝同色；每个节点用短词且结构平行。

案例：提升用户留存

和结构图的区别

它俩最容易混，因为脑图收敛之后，往往就变成了结构图。区别在于阶段与气质：脑图重发散（还在想、用曲线、随意生长）；结构图重收敛后的稳定结果（已想清楚、用直角、正式规整，能写进 PRD）。

思维导图 · 发散（曲线）
结构图 · 收敛（直角）
工具：XMind 是脑图的强项，左手敲键盘即可成图——Tab 加子主题、Enter 加同级；用「向右逻辑图」结构 + 现成风格主题最快出好看的图。
流程行为

流程图 / 泳道图

回答：「事情按什么顺序发生？每一步归谁做？」

是什么

流程图讲清一连串动作的先后顺序；泳道图 = 流程图 + 按角色分行，每条「泳道」一个角色，每个步骤画进负责它的那条道里。跨泳道的箭头就是职责交接——这正是泳道图最值钱的信息。

符号只用四个：圆角矩形＝开始/结束、矩形＝步骤、菱形＝判断（能用是/否回答）、箭头＝流向。判断的每个出口都要标条件。

案例：内容发布审核

和状态图的区别（关键对照）

同一件「订单退款」，用流程图和状态图画出来完全不同。流程图的方框是动作（动词），讲事情怎么走、谁来做，用菱形分岔；状态图的方框是状态（名词），讲一个对象会变成哪些样子，动作全跑到箭头上。

流程图 · 方框＝动作
状态图 · 方框＝状态

注意「审核驳回」：流程图里它是一个动作框，状态图里它是一条绕回去的箭头（退款中 → 已支付）。状态图天然允许回头路，流程图则尽量单向。

工具：泳道图用 ProcessOn（自带泳道模板）或 draw.io 最顺手，XMind 不适合。
诊断技巧：若某角色的步骤东一块西一块、箭头反复横跨泳道，说明流程本身交接太多、该优化了。
流程行为

状态图（状态机）

回答：「一个对象会处在哪些状态？什么事件让它变？」

是什么

它逼你想全一个对象的所有状态和流转，最大价值是把超时、取消、退款、失败这些容易漏掉的边界情况全摊出来——这是 PM 严谨度最被研发认可的地方。

两个核心零件：方框＝状态（名词），是能存进数据库的「待着的样子」；箭头＝事件（动词），是让它跳转的触发条件，必须写在箭头上。还有起始点（实心圆点）和终态（只进不出）。

案例：订单状态机

和流程图的区别

口诀：描述「先做什么再做什么、谁来做」用流程图；描述「这东西会变成哪些样子、什么事件让它变」用状态图。两者的对照图见上一章「流程图 / 泳道图」的退款双图。实际工作里常搭配用：流程图给协作方讲清怎么办事，状态图给研发兜住所有状态和异常。

铁律：画完逐个框检查「有没有进、有没有出」——除起始态和终态外，进得去出不来＝死状态，没箭头指向＝到不了的废状态，都说明漏设计了。
工具：draw.io（自带 UML 状态机图形）或 ProcessOn。
结构组成

架构图

回答：「系统由哪些部分组成？谁和谁连？」

是什么

架构图讲结构关系，几乎都靠一个心法撑起来——分层。最经典是三层架构：接入层（客户端）→ 业务层（服务）→ 数据层。它不是「固定几层」，而是以三层为底、按职责按需增减（加网关层、中台层、基础设施层等）。

案例：分层产品架构

最大的坑——箭头别画满！别把每个客户端连到每个服务、再连到每个库，画成 N×N 蜘蛛网。架构图是给人看结构的，不是数连线的。需要强调某条链路时，再单独画一张子图。
给 PM：产品架构图 3–4 层就够，中间件 / 基础设施那种细节是研发的技术架构图才需要。

和结构图的区别

一句话：架构图按「职责」把系统横切成层（接入/业务/数据）；结构图按「包含/归属」往下分解成树（产品→模块→功能）。前者回答「怎么协作运转」，后者回答「由什么组成」。详见下一章。

结构组成

结构图

回答：「什么由什么组成？什么包含什么？」

是什么

按「包含 / 归属」关系往下分解成树。它没有固定层数，几层取决于你拆多细（常规 3–4 层）。PM 用的主要两种：功能结构图（节点是「功能」——能做什么）和信息架构图 / IA（节点是「页面」——有哪些页、怎么导航）。

案例：同一个「外卖 App」的两种结构图

下面两张骨架完全一样，差别全在节点里装的是什么——这正是关键。左边末端是「能做的事」（动作），右边末端全带个「页」字（页面）。

功能结构图 · 节点＝功能
信息架构图 · 节点＝页面

记忆点：形状都是树，看节点——装「能做什么」就是功能结构图，装「有哪些页面」就是信息架构图。跟研发讲要做哪些功能用前者；规划页面、Tab、导航跳转用后者。

最易翻车的一条：同一层必须是「同粒度、同一类」——别把「搜索」（一个功能点）和「整个交易体系」（一个大模块）放同一层。同层节点应平级、互不重叠，争取 MECE。
工具：结构图正是 XMind 强项（切「组织结构图/树状」结构即可），ProcessOn、draw.io 也行。
分析决策

优先级矩阵（四象限）

回答：「这么多需求，先做哪个？」

是什么

用两个维度把需求切进田字格，把「都很重要」的争论变成一张图上的位置问题。最经典是价值 vs 投入。关键在于：四个象限不只是分类，每个都对应一个行动（优先做 / 规划 / 有空做 / 砍掉）。

案例：价值 - 投入矩阵

易踩的坑：两个维度必须相互独立。「价值」和「成本」是两件事，可以；别选「重要」和「价值」这种其实是一回事的维度。
其他常见版本：重要-紧急四象限（艾森豪威尔，管时间）、RICE（算分排序）、Kano 模型（分需求类型）。这个图最省事，Excel / PPT / 白板都能画。
界面体验

用户旅程图

回答：「用户用我们产品时，体验怎么一路起伏？」

是什么

站在用户视角，沿时间轴画出完成某目标的全过程：每个阶段的行为、痛点，尤其是那条情绪曲线。它的灵魂就是找到情绪低谷——低谷就是机会点，告诉你最该投入资源去改哪里。

案例：新用户点外卖

和流程图的区别

流程图是系统视角，讲「事情怎么走」，没有情绪；旅程图是用户视角，讲「用户怎么感受、心情怎么起伏」。同样是「等待配送」，流程图里是中性步骤，旅程图里是情绪暴跌的痛点。它真正的杀伤力是让需求有据——把「我觉得要加进度条」变成「用户体验在等待阶段跌到谷底」。

最大的坑（铁律）：情绪曲线必须基于真实用户调研 / 访谈 / 数据，不能坐在工位上自己编。
工具：FigJam、Miro、ProcessOn，本质是张表格。
界面体验 · 进阶

服务蓝图

回答：「用户的体验，背后靠什么在支撑？」

是什么

用户旅程图的「立体升级版」。同一条时间轴，纵向切成几层，把用户看得见的体验和背后看不见的运营、系统对齐着摊开。那条「可见线」是灵魂：线上是用户能感知的，线下是决定体验却看不见的支撑。

案例：外卖配送服务蓝图

和用户旅程图的区别

旅程图只画「可见线以上」（用户视角 + 情绪），告诉你哪儿体验差；服务蓝图补上「可见线以下」，告诉你为什么差、该改后台哪个环节。例：旅程图发现「等待阶段进度不透明」，服务蓝图进一步定位到——前台「配送进度页」不透明，根因在后台「调度系统」没把骑手实时位置回传上来。

什么时候用：当体验问题不只是 UI、而牵扯多个团队 / 后台系统 / 线下运营时。它偏服务设计和跨团队拉通，对纯做 App 的 PM 属于「了解、需要时能画」这一档。工具：Miro、FigJam（常多人协作填写）。
