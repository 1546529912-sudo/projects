# 模块五：系统设置

> CRM 学习路径：✅ 客户管理 → ✅ 跟进记录 → ✅ 销售管理 → ✅ 数据报表 → ✅ **系统设置**

---

## 一、是什么？

系统设置是 CRM 的**底层操作系统**。前四个模块是业务功能，系统设置控制这些功能如何运转——字段怎么定义、角色怎么分配、流程怎么自动化、数据怎么统一，都在这里配置。

**产品经理视角：** 系统设置 = 给运营/管理员的「低代码平台」。设计好坏决定 CRM 能否随业务灵活演化，能否让运营自己完成 80% 的配置需求，而不是每次改个字段就要找开发。

衡量标准：
- **灵活性**：业务变了，配置能跟上吗？
- **安全性**：权限能防止误操作吗？
- **可维护性**：配置了什么、谁配的、什么时候改的，有审计日志吗？

---

## 二、六大功能模块

| 模块 | 核心职责 | 影响范围 |
|------|---------|---------|
| 用户与权限 | 角色设计、数据权限、字段级控制 | 谁能看什么、能做什么 |
| 字段与表单 | 自定义字段类型、必填规则、表单逻辑 | 所有录入界面 |
| 流程自动化 | 触发器、工作流规则、自动分配 | 业务流转效率 |
| 数据字典 | 枚举值管理、标签体系 | 报表维度一致性 |
| 通知与提醒 | 消息模板、提醒规则 | 销售行动及时性 |
| 集成与 API | 第三方对接、Webhook、数据同步 | 系统互通 |

### 系统设置如何影响其他模块

| 模块 | 影响关系 |
|------|---------|
| 客户管理 | 字段配置 + 权限控制，决定销售能看到/编辑哪些客户信息 |
| 跟进记录 | 通知配置，决定超期跟进时谁收到提醒、如何提醒 |
| 销售管理 | 流程自动化，决定商机在阶段间如何流转和自动更新 |
| 数据报表 | 数据字典，决定报表维度的枚举一致性和可汇总性 |

## 三、用户与权限

### 3.1 权限的两个维度

权限有两条独立的轴，必须分开理解：

**功能权限** — 控制「能做什么操作」
- 查看客户列表、编辑客户信息、删除客户、导出数据、查看报表
- 技术实现：控制按钮、菜单是否可见/可点

**数据权限** — 控制「能看到哪些数据行」
- 仅自己负责的客户 / 本组所有客户 / 本部门所有客户 / 全公司所有客户
- 技术实现：控制 SQL WHERE 条件，过滤数据行

> 两个维度是独立配置的。一个销售可以有「编辑客户」的功能权限，但数据权限限制他只能看到自己负责的客户——他能编辑，但范围受限。

---

### 3.2 典型角色体系

| 角色 | 功能权限 | 数据范围 |
|------|---------|---------|
| 超级管理员 | 所有功能，含系统设置、用户增删改 | 全公司所有数据 |
| 销售管理员/总监 | 查看+编辑、查看报表、分配线索 | 本部门所有客户 |
| 销售组长 | 查看+编辑、查看组报表、不能删除 | 本组所有客户 + 自己客户 |
| 普通销售 | 查看+编辑、无删除、无导出、无报表 | 仅自己负责的客户（Owner = 自己） |

---

### 3.3 三个关键设计决策

#### 决策 1：角色制（RBAC）还是属性制（ABAC）？

| | RBAC — 基于角色 | ABAC — 基于属性 |
|-|----------------|----------------|
| 规则方式 | 给人打角色标签，角色有固定权限集合 | 权限由属性条件组合决定 |
| 规则示例 | 「张三 = 销售」 | 「地区=华东 AND 级别≥3 才能看华东大客户」 |
| 适用场景 | 小团队、权限边界清晰 | 多地区多业务线、权限规则复杂 |
| 维护成本 | 低 | 高 |

**判断标准：** 能用职位描述清楚权限边界 → 用 RBAC；需要多条件组合才能描述 → 用 ABAC。90% 的中小公司 RBAC 够用。

#### 决策 2：数据权限用「Owner 字段」还是「层级继承」？

**Owner 字段：** 每条记录有归属人，只能看 Owner = 自己的数据。简单、最常见，换人需手动转移。

**层级继承：** 上级自动看到下级所有数据。依赖组织架构树维护准确，架构混乱则权限必乱。

> 实际系统通常两者结合：Owner 控制行级，层级继承控制管理层可见性。
> 
> ⚠️ 陷阱：组织架构表必须和实际业务强绑定。很多公司 HR 系统里的汇报关系和实际销售管理关系不一致，层级继承做进系统后一旦架构调整，权限全乱。

#### 决策 3：要不要做字段级权限？

**场景：** 销售能看客户名称和联系方式，但看不到「合同金额」和「竞品报价」。

**实现成本高：** 前端隐藏 + 后端 API 过滤 + 导出过滤，三处都要改。新增字段每次都要再改三个地方。

**推荐做法：** 把需要保护的字段归到同一个 Tab（如「商务信息」），对整个 Tab 做权限控制，而不是对每个字段单独控制。

**对比：**

| | 字段级权限 | Tab 级权限 |
|-|-----------|-----------|
| 前端 | 每个字段单独判断权限再渲染 | 判断一次 Tab 权限，整个 Tab 不渲染 |
| API | 返回时按字段过滤 | 整个接口直接 403 |
| 导出 | 每列单独判断 | 整个 Tab 字段统一排除 |
| 新增字段 | 每次都要改三个地方 | 放进 Tab 自动继承权限 |
| 用户体验 | 锁头图标，体验差 | Tab 灰色不可点，认知清晰 |

> **PM 判断原则：** 先问这些需要保护的字段能不能在信息架构上归到一起。能归到一起就用 Tab 整体控制；真的打散在各处才考虑字段级权限——而且这种情况在 CRM 里很少见。

---

### 3.4 不能忽视：权限变更审计日志

谁在什么时间给谁修改了权限，必须有记录。出了数据泄露事故，第一件事就是查权限变更历史。这个往往在立项时没人提，上线后才想起来。

## 四、字段与表单配置

### 4.1 自定义字段类型全景

#### 基础输入类

| 类型 | 适用场景 | 注意事项 |
|------|---------|---------|
| 单行文本 | 客户名称、联系人姓名 | 可设最大长度；结构化数据（手机号、邮编）不要用这个 |
| 多行文本 | 备注、客户需求描述 | 不可排序、不可做筛选条件，纯记录用 |
| 数字/金额 | 合同金额、员工人数 | 金额要单独处理货币单位和精度，不要用普通数字字段存 |
| 日期/日期时间 | 合同到期日、首次接触时间 | 存 UTC、展示本地时区；跨时区团队必须统一 |
| 布尔（是/否） | 是否签署 NDA、是否上市公司 | 只有两个值时才用；三个值用单选，不要用两个布尔拼 |
| 手机/邮箱/网址 | 联系电话、公司邮箱 | 带格式校验；手机号要考虑国际区号 |

#### 选择类

| 类型 | 适用场景 | 注意事项 |
|------|---------|---------|
| 单选下拉 ★最常用 | 客户状态、行业、来源 | 枚举值来自数据字典；选项建议不超过 15 个 |
| 多选 ⚠️慎用 | 感兴趣产品、客户标签 | 存储为数组；统计时需要展开，报表设计要注意 |
| 评分/星级 | 客户意向度、线索质量 | 本质是 1-5 的数字；可参与排序和平均值计算 |

#### 关联类

| 类型 | 适用场景 | 注意事项 |
|------|---------|---------|
| 关联对象 ★核心 | 联系人关联到客户、商机关联到联系人 | 决定模块之间如何连接 |
| 归属人（Owner）⚠️影响权限 | 客户负责销售 | 特殊的用户关联字段，直接影响数据权限过滤 |
| 公式字段 | 合同剩余天数、折扣后金额 | 由其他字段计算得出，只读 |

#### 高级类

| 类型 | 适用场景 | 注意事项 |
|------|---------|---------|
| 地址 ⚠️易踩坑 | 公司地址 | 省市区要拆开存，不要存一整串字符串，否则无法按省筛选 |
| 文件/图片 | 名片照片、合同扫描件 | 存 URL 而非文件本身；要考虑存储成本和访问权限 |
| 自动编号 | 客户编号 CUS-20240001 | 系统生成，不可编辑 |

---

### 4.2 必填规则的四种类型

#### 类型一：全局必填
任何人、任何时候保存都必须填。适合：客户名称、联系电话。

#### 类型二：阶段必填（最重要）
进入某阶段才触发，是销售流程的「质量门」。

```
新线索   →   初步接触      →   报价中         →   谈判中       →   赢单
         电话必填        联系人必填        报价单必填     合同金额必填
```

每个阶段卡一道门，保证数据完整性随流程推进逐步提升，销售阻力也小（不是一开始就要求填 20 个字段）。

#### 类型三：角色必填
特定角色保存才触发。例如管理员新建客户 → 来源必填；普通销售新建 → 来源可选。

#### 类型四：条件必填
另一字段的值触发。例如客户类型 = 企业 → 营业执照号必填；客户类型 = 个人 → 营业执照号隐藏。

---

### 4.3 表单设计三个核心决策

#### 决策 1：一张表单放多少字段？

新建时只放核心 3-5 个必填字段，其余进入详情页后补录。

- **反例：** 一次性要求填 20 个字段 → 销售嫌麻烦，随便填或不填，数据质量反而更差
- **正例：** 先进系统，边跟进边完善，销售阻力小

#### 决策 2：字段动态显隐（条件逻辑）

字段 A 的值 → 控制字段 B 的显示/隐藏/必填状态。

规则链不要超过 3 层，否则销售无法预测表单行为，运营也难以维护。

#### 决策 3：默认值怎么设？

| 类型 | 示例 | 说明 |
|------|------|------|
| 固定默认值 | 客户状态 = 「潜在客户」 | 新建时自动填入，销售可修改 |
| 动态默认值 | 归属人 = 当前登录用户 | 根据上下文自动计算，不需要销售填写 |
| 继承默认值 | 商机地区继承自客户地区 | 从关联对象带过来，可覆盖 |

> **PM 原则：** 能系统自动填的，绝不让销售手动填。每减少一个手动输入，就减少一个出错机会和一分填写摩擦。

---

### 4.4 高频踩坑：字段修改的向后兼容

| 操作 | 风险 | 处理方式 |
|------|------|---------|
| 加字段 | 安全 | 历史数据该字段为空，不影响已有记录 |
| 改字段名 | 表面安全，实际危险 | 报表、导出模板、对接系统写死了字段名会出问题。应改显示名，不改内部 key |
| 删除枚举选项 | 危险 | 历史数据里选了该值的记录字段值变成不存在的枚举，报表统计出 null |

> **核心原则：** 枚举值只允许停用，不允许删除。停用后历史数据保留原值，只是新建时不再出现该选项。

## 五、流程自动化

### 5.1 触发器的四种类型

| 类型 | 触发时机 | 示例 | 注意事项 |
|------|---------|------|---------|
| 记录变更触发 ★最常用 | 记录被创建/修改/删除时 | 商机阶段从「接触」变为「报价」 | 精确、即时，是主力触发方式 |
| 定时触发 ⚠️易遗忘 | 到达时间点，或距某字段 N 天 | 合同到期前 30 天；最后跟进超过 7 天 | 依赖定时任务（cron）；要考虑时区 |
| 条件触发 | 字段值达到阈值 | 商机金额 > 500,000 | 单独用容易重复触发，一般作为事件触发的过滤条件 |
| 外部触发 | Webhook/API 推送 | 官网表单提交推送到 CRM | 需要双方约定数据格式 |

> **触发器 ≠ 执行动作。** 触发器只是「检测到某件事发生了」，后面还需要过滤条件和具体动作。三者合起来才是一条完整的工作流规则。

---

### 5.2 工作流规则的完整结构

一条工作流规则 = **触发器 + 过滤条件 + 动作 + 执行设置**

**示例：大额商机进入报价阶段 → 通知总监 + 更新优先级**

```
① 触发器    商机记录被修改，且「阶段」字段发生变化
      ↓
② 过滤条件  新阶段 = "报价" AND 商机金额 > 500,000 AND 客户类型 = "企业"
      ↓
③ 执行动作  → 更新字段：优先级 → 高
            → 发送通知：通知销售总监（站内信 + 邮件）
            → 创建任务：7天后提醒归属销售跟进
            → 调用 Webhook：推送到 BI 系统
      ↓
④ 执行设置  每条记录只触发一次 / 失败则告警给管理员
```

**可配置的动作类型：**

| 动作 | 说明 |
|------|------|
| 更新字段 | 修改记录的某个字段值 |
| 发送通知 | 站内信/邮件/企业微信，支持模板变量 |
| 创建任务 | 生成跟进提醒，可设延迟时间 |
| 分配记录 | 自动分配给对应销售 |
| 调用 Webhook | 推送事件到外部系统 |
| 延迟等待 | N 小时/天后继续执行后续动作 |

---

### 5.3 执行设置的关键：防死循环

> ⚠️ **死循环陷阱：** 动作触发字段变更 → 再次满足触发条件 → 无限循环。几秒钟可以把数据库写满。

**必须设置「每条记录只触发一次」的防重机制，这是系统级保护，不能靠运营自己注意。**

系统还应该实时检测潜在循环风险：当工作流同时满足「触发条件监听字段变更」+「动作会修改字段」时，主动提示运营调整执行设置。

---

### 5.4 自动分配的完整决策逻辑

自动分配是流程自动化里最复杂的一块，核心认知：**「谁录入归谁」只是线索来源的其中一种，且往往不是主流的那种。**

| 线索来源 | 分配逻辑 | 原因 |
|---------|---------|------|
| 销售自己开发的客户 | 归录入人（销售本人） | 这才是「谁录入归谁」的场景 |
| 官网表单/广告投放 | 按地区/行业自动分配 | 没有录入人，规则引擎决定 |
| 展会名片/批量导入 | 轮流制/按负载分配 | 录入人是运营，不应归运营负责 |
| 大客户/战略线索 | 手动指定/管理员分配 | 不走规则，人工决定 |
| 客服/售后转来 | 归原客户负责销售 | 保持客户关系连续性 |

**自动分配的四个步骤：**

**第一步：匹配策略（决定候选池）**
- 规则匹配：按线索属性和销售属性对齐，筛出候选人集合
- 指定分组：直接指定某个销售组
- 全量参与：所有在线销售都参与分配

**第二步：负载均衡（候选池里分给谁）**
- 轮流制（Round Robin）：A → B → C → A，公平简单
- 负载均衡（推荐）：谁手里激活线索数最少，分给谁
- 权重制：按销售能力/意愿设权重，高权重多分

**第三步：可用性过滤（分配前排除不可分配的人）**
- 状态排除：休假中、离职、停用账号的销售不参与分配 ⚠️容易漏做
- 上限控制：每人设置最大激活线索数上限，达到上限暂停分配

**第四步：兜底机制（所有规则都没匹配到时）**
- 候选池为空 → 分配给默认负责人 + 发送告警通知给管理员
- 规则未覆盖 → 进入待分配队列 + 记录未匹配原因，方便运营补充规则

> **PM 核心原则：任何线索都不能「消失在系统里」。** 兜底机制是自动分配能否在生产环境稳定运行的关键。

**自动分配为什么需要人员/组织标签：**

自动分配规则的本质是一个**匹配游戏**：
- 左边：线索的属性标签（来自哪、什么行业、什么地区）
- 右边：销售的属性标签（负责哪个地区、哪个行业、在哪个组）

两边对上了才能分配。所以用户管理里，管理员必须预先维护销售的：负责地区、擅长行业、所属销售组、当前激活状态。这些字段不是销售自己填的，是管理员在系统设置中配置的。

**这条链路揭示了系统设置各模块的强耦合关系：**
> 数据字典定义枚举值（「华东」是什么）→ 用户管理给销售打标签（张伟负责华东）→ 自动分配规则引用这些标签（华东线索 → 张伟）

任何一环断了，整个分配逻辑就失效。

### 5.5 配置界面的交互设计原则

| 设计点 | 说明 |
|-------|------|
| 左右分栏布局 | 左侧规则列表（索引层），右侧单条规则编辑器（详情层），快速切换 |
| 四步线性结构 | 触发器 → 过滤条件 → 动作 → 执行设置，按因果链排列，顺序不能打乱 |
| 字段选项联动 | 触发对象切换后，条件字段选项同步更新，不能出现不属于当前对象的字段 |
| 动作用卡片选择器 | 图标+名称+说明，比下拉列表识别效率高 |
| 循环风险实时警告 | 配置过程中即时检测，不等保存时才报错 |
| 新建默认停用 | 运营配完检查无误再手动启用，不是保存即生效，防止规则配错批量影响数据 |

---

## 六、数据字典与标签管理

### 6.1 数据字典是什么

数据字典统一管理 CRM 里所有下拉选项（枚举值），解决「同一个概念被写成 N 种说法」的问题。

**没有数据字典的后果：** 「客户来源」一个字段，各人填法：官网、官方网站、公司网站表单、website……同一来源 7 种写法，报表里出现 7 个条目，数据完全无法汇总。

**有数据字典后：** 所有人从同一个列表选 → 报表精准，可按来源分析转化率。

---

### 6.2 需要字典管理的核心字段

| 字段 | 典型枚举值 | 影响 |
|------|---------|------|
| 客户来源 | 官网表单、广告投放、展会、朋友介绍、电话开发、合作伙伴、客户转介绍 | 来源分析 |
| 行业分类 | 制造业、零售、金融、医疗、教育、房地产、互联网、政府 | 自动分配 |
| 客户状态 | 潜在客户、跟进中、已报价、谈判中、成交、流失、暂缓 | 流程流转 |
| 丢单原因 | 价格太高、选了竞品、需求不匹配、预算冻结、时机不对 | 复盘分析 |
| 客户规模 | 1-50人、51-200人、201-1000人、1000人以上、上市公司 | 销售策略 |
| 地区 | 华东、华南、华北、华中、西南、西北、东北、港澳台、海外 | 自动分配 |

---

### 6.3 枚举值维护的核心规则

**只允许停用，不允许删除。**

停用后该选项不再出现在下拉列表中，但历史已选此值的记录数据完整保留。删除枚举值会破坏历史数据——历史记录里的值变成不存在的枚举，报表统计出 null，筛选出错。

**停用时应提示影响范围：** 「确认停用「华东」？历史已有 287 条记录选择了此值，停用后这些记录数据不受影响，但新建时不再出现此选项。」

**排序：** 枚举值支持拖拽排序，高频选项置顶减少操作成本。

---

### 6.4 枚举值 vs 标签——两种不同的机制

| 对比 | 枚举值（单选/多选下拉） | 标签（自由多标签） |
|------|--------------------|--------------------|
| 本质 | 一个字段，一个固定值 | 一个字段，多个自由值 |
| 管理方式 | 管理员统一维护，用户只能选 | 用户可自建，也可从已有标签中选 |
| 用途 | 有明确业务语义，用于规则匹配和报表维度 | 灵活补充描述，不适合做规则匹配 |
| 存储方式 | 单值字段 | 数组 |
| 示例 | 制造业、华东、成交 | KA客户、有复购潜力、决策链复杂 |

**四种场景的选择判断：**

| 场景 | 用哪个 | 理由 |
|------|-------|------|
| 客户行业 | 枚举值 | 自动分配规则要匹配行业，必须是固定值 |
| 客户特征描述 | 标签 | 主观判断、多样化，枚举无法穷举 |
| 感兴趣的产品线 | 枚举多选 | 产品线有限，需要精确统计 |
| 销售自定义备注分类 | 标签 | 每个销售分类方式不同，强制统一阻力大 |

---

### 6.5 标签体系的三个设计决策

**谁能创建标签？**
全员可创 → 标签爆炸，几个月后出现几百个含义相近的标签。推荐：销售可选已有标签，新建需管理员审核。

**标签能搜索/筛选吗？**
可以，但性能代价高。标签是数组存储，按标签筛选需要全表扫描。高频筛选的标签最好「升格」为枚举字段，性能差几个数量级。

**标签要不要分类？**
标签多了之后，建议分组管理：客户特征类、跟进状态类、内部运营类。分组后选标签时有导航，用户不需要从几百个标签里盲找。

> **PM 判断口诀：** 这个值「需要被规则引用」吗？需要 → 枚举值。只是「方便人阅读」吗？→ 标签。一旦某个标签被大量销售用于筛选，就说明它该升格为枚举字段了——这是数据字典持续演进的信号。

## 七、模块间的数据语言统一

系统设置最核心的价值不是单个功能，而是**让各模块用同一套「语言」说话**。

```
数据字典        定义枚举值    「华东」是什么
    ↓
用户管理        给销售打标签  张伟负责地区 = 华东
    ↓
自动分配规则    引用标签      华东线索 → 张伟
    ↓
数据报表        汇总维度      按地区统计线索转化率
```

任何一环用了不同的「语言」（比如字典里写「华东」，用户档案里写「上海」），整条链路就断了。这就是为什么枚举值必须统一管理，不能让各人自由填写。

## 八、系统设置设计全局视角

| 设计原则 | 说明 |
|---------|------|
| 灵活性优先 | 业务变化快，字段/规则/权限要能快速调整，不依赖开发 |
| 安全防线 | 权限粒度要够细，关键操作要有审批和日志 |
| 运营友好 | 配置界面对非技术运营人员要可理解，不是给工程师用的 |
| 保护历史数据 | 枚举不删只停用，字段改名不改 key，版本变更有兼容策略 |
| 防止过度配置 | 不是功能越多越好，配置太复杂运营反而不会用 |
