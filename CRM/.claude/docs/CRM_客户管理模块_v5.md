# CRM 客户管理模块详解 v5

> 学习路径：⏭ **模块一：客户管理（当前）** → ⬜ 模块二：跟进记录 → ⬜ 模块三：销售管理 → ⬜ 模块四：数据报表 → ⬜ 模块五：系统设置

## 一、核心概念

### 1. 线索、客户、联系人的区别

| 概念 | 英文 | 解释 | 举例 |
|------|------|------|------|
| 线索 | Lead | 还未验证购买意向的潜在客户 | 展会上扫码留名片的人 |
| 客户 | Customer | 有明确意向或已成交的公司 | 主动询价或已付款的公司 |
| 联系人 | Contact | 客户公司里具体对接的人 | 腾讯的采购经理张三 |

> 核心区别：**客户是公司，联系人是公司里的人。** 一个客户可以有多个联系人。

### 2. 整体流转逻辑

```
线索 (Lead)
    ↓  销售跟进、判断有意向
    ↓  【转化】
客户 (Customer)  +  联系人 (Contact)
    ↓
商机 (Opportunity)
    ↓
成交 / 流失
```

### 3. 数据关联关系

```
线索 (Lead)
│
└─ 转化后生成
        │
        ├─ 客户 (Customer) ──── 一对多 ────  联系人 (Contact)
        │
        └─ 商机 (Opportunity)
                │
                └─ 成交后生成 ──── 订单 / 合同
```

## 二、线索模块（Lead）

### 线索从哪里来？

| 来源 | 说明 |
|------|------|
| 手动录入 | 销售员自己填，比如展会名片 |
| 表单导入 | 批量上传 Excel |
| 系统自动导入 | 官网表单填写后自动进入 CRM |
| 广告平台 | 百度、微信广告留资自动同步 |

### 线索来源字段设计

**推荐方案：两层下拉选择 + 其他可填写**

| 第一层（大类） | 第二层（小类） |
|-------------|-------------|
| 线上广告 | 微信广告、百度广告、抖音广告 |
| 线下活动 | 展会、沙龙、地推 |
| 客户推荐 | 老客户介绍、合作伙伴介绍 |
| 自主开发 | 电话开发、登门拜访 |
| 其他 | 文本框填写 |

**设计要点：**
- 选项在后台可配置，管理员可增删改
- 选项只能停用，不能随意删除（防止历史数据丢失）
- 停用后的影响：新建时不显示、编辑已用该选项时显示但标注"已停用"、报表中历史数据仍然统计

**停用场景举例：**
- 渠道不再投放（如停止知乎广告）
- 选项名称需要更改
- 手误创建了重复或错误的选项
- 公司业务转型，整体替换渠道体系

### 线索核心字段

**基本信息**
- 姓名、手机号、邮箱、公司名称、职位

**来源信息**
- 线索来源（大类）、来源渠道（小类）、录入时间

**状态信息**
- 线索状态（未跟进 / 跟进中 / 已转化 / 已无效）
- 负责销售、最近跟进时间

### 线索来源字段：单选还是多选？

**销售员录入时：单选，保持简单。**

销售员手动录入线索时，只填当下这次的来源渠道，不需要知道这个人之前是否通过其他渠道接触过公司。

```
来源渠道：[下拉选择]  展会
```

**多来源的场景从哪里来？**

多来源几乎不来自销售员手动录入，而是来自以下两种情况：

```
情况一：不同销售员分别录入了同一个人
销售员A  1月录入张三  来源=百度广告
销售员B  2月录入张三  来源=展会
→ 两条都进入系统，等管理员合并

情况二：系统自动导入
官网表单  1月  张三留资   自动进入CRM  来源=官网
展会扫码  2月  张三扫码   自动进入CRM  来源=展会
→ 系统自动产生两条，等管理员合并
```

**为什么销售员手动录入不会出现多来源？**

因为查重机制会拦住。销售员第二次录入同一个人时，输入手机号光标离开，系统立即提示：

```
⚠️ 该手机号已存在于你的线索中
线索名称：张三  创建时间：2026-01-15  来源：百度广告
[查看该线索]  [继续新建]
```

销售员看到提示就不会重复录入了。多来源的情况，交给管理员在合并时处理。

### 线索转化

线索和客户是两张独立的表，字段不同、用途不同：

```
线索表                    客户表
─────────────────         ─────────────────
姓名                      公司名称
手机号                    行业
邮箱                      公司规模
公司名称                  客户级别
职位                      客户状态
线索来源                  负责销售
线索状态
                          联系人表
                          ─────────────────
                          姓名
                          手机号
                          邮箱
                          职位
                          决策角色
                          所属客户
```

**转化的本质：** 以线索为原材料，同时创建客户和联系人两条新记录：
- 公司相关字段 → 填入客户表
- 个人相关字段 → 填入联系人表

**转化界面设计：**

```
┌─────────────────────────────────────────┐
│ 线索转化                                │
├─────────────────────────────────────────┤
│ 【将创建客户】                           │
│ 公司名称：腾讯科技      ✅ 自动填入      │
│ 行业：互联网            ✅ 数据库拉取    │
│ 规模：10万人以上        ✅ 数据库拉取    │
│ 客户级别：A类           ✅ 规则自动推断  │
│ 负责销售：张三          ✅ 继承线索      │
│ 客户状态：跟进中        ✅ 系统默认      │
│                                         │
│ 【将创建联系人】                         │
│ 姓名：张三              ✅ 自动填入      │
│ 手机：138****8888       ✅ 自动填入      │
│ 职位：采购经理          ✅ 自动填入      │
│ 决策角色：___________   ✏️ 需要手填      │
│                                         │
│ 【是否同时创建商机】                     │
│ ☑ 创建商机                              │
│ 商机名称：腾讯科技-采购项目 ✅ 自动生成  │
│ 预计金额：___________   ✏️ 需要手填      │
│                                         │
│          [取消]      [确认转化]          │
└─────────────────────────────────────────┘
```

**转化时自动填入的信息分四类：**

| 类型 | 说明 | 举例 |
|------|------|------|
| 线索字段直接带入 | 线索里有的字段自动对应填入 | 姓名、手机、公司名称 |
| 系统自动生成 | 不需要任何人填 | 创建时间、客户状态默认"跟进中" |
| 第三方数据库拉取 | 对接企查查/天眼查获取工商数据 | 行业、规模、注册资本、经营状态 |
| 规则自动推断 | 管理员预设规则，系统自动判断 | 规模超1000人自动定为A类客户 |

**为什么用企查查而不是 AI 大模型？**

| 能力 | 企查查/天眼查 | AI 大模型 |
|------|------------|---------|
| 工商注册信息 | ✅ 准确实时 | ❌ 可能过时或编造 |
| 经营状态 | ✅ 实时更新 | ❌ 不可靠 |
| 小公司信息 | ✅ 全部覆盖 | ❌ 几乎不知道 |
| 行业背景分析 | ❌ 只有基础信息 | ✅ 擅长 |
| 智能跟进建议 | ❌ 不会 | ✅ 擅长 |

> 最佳方案：**企查查提供准确的结构化数据，AI 大模型做深度分析和建议，两者互补使用。**

**转化设计要点：**
- 转化时系统自动把线索信息填充到客户和联系人，不重复填写
- 转化后原线索标记为"已转化"，保留不删除
- 是否同时创建商机，由销售员自己勾选
- 线索详情页记录转化结果，客户详情页记录来源线索，互相关联

## 三、客户模块（Customer）

### 核心字段

**公司信息**
- 公司名称、行业、公司规模、地区、官网

**状态信息**
- 客户级别（A / B / C 类）
- 客户状态（跟进中 / 已成交 / 已流失）
- 负责销售、来源线索

### 客户级别

客户级别是对客户**价值高低的分类标签**，帮助销售员分配时间和精力。

**评估维度：**

| 维度 | 说明 |
|------|------|
| 预算规模 | 客户能花多少钱 |
| 成交概率 | 有多大可能购买 |
| 决策周期 | 多久能成交 |
| 战略价值 | 能否带来更多客户或行业影响力 |

**级别对系统的联动影响：**
- 客户列表默认按级别排序，A类排最前
- 跟进提醒频率不同（A类3天未跟进提醒，B类7天，C类30天）
- 报表分析时按级别分类统计
- 公司资源优先分配给A类客户

**推荐评估模型：**

| 模型 | 适合场景 | 维度数量 |
|------|---------|---------|
| BANT | 中小型团队，前期快速筛选 | 4个 |
| SCOTSMAN | 大客户销售，深度跟进阶段 | 8个 |

**BANT 模型（前期使用）：**

| 字母 | 英文 | 中文 | 满分 |
|------|------|------|------|
| B | Budget | 预算 | 3分 |
| A | Authority | 决策权 | 3分 |
| N | Need | 需求 | 3分 |
| T | Timeline | 时间 | 3分 |

```
总分 9-12 分  →  A 类客户
总分 5-8 分   →  B 类客户
总分 0-4 分   →  C 类客户
```

**SCOTSMAN 模型（后期使用）：**

| 字母 | 英文 | 中文 | 核心问题 |
|------|------|------|---------|
| S | Solution | 解决方案匹配度 | 我们的产品能解决客户的问题吗？ |
| C | Competition | 竞争情况 | 竞争对手是谁？我们处于什么位置？ |
| O | Originality | 独特优势 | 相比竞品我们有什么差异化优势？ |
| T | Timeline | 时间节点 | 客户什么时候要做决策？ |
| S | Size | 规模/金额 | 这个单子值多少钱？ |
| M | Money | 预算和资金 | 客户有没有钱？预算审批了吗？ |
| A | Authority | 决策权 | 你在跟的人能拍板吗？ |
| N | Need | 需求迫切度 | 客户问题有多痛？ |

```
总分 19-24 分  →  A 类（重点跟进，全力推进）
总分 11-18 分  →  B 类（正常跟进，持续培育）
总分 0-10 分   →  C 类（低频维护，等待时机）
```

**如何区分前后期，切换评估模型？**

```
客户状态 = 跟进中          →  使用 BANT（信息少，快速判断）
客户状态 = 意向客户/谈判中  →  切换 SCOTSMAN（信息足，深度评估）
```

切换时 BANT 已填字段自动带入 SCOTSMAN 对应维度（B→M，A→A，N→N，T→T），销售员只需补充新增的 4 个维度。

### 客户状态流转

```
跟进中 → 意向客户 → 谈判中 → 已成交
                              ↓
                           已流失
```

**三种触发方式：**

1. **销售员手动改**：在客户详情页直接点选状态
2. **关联动作自动触发**：创建订单自动变为"已成交"
3. **跟进时顺带更新**：填写跟进记录时同步更新状态

**推荐方案：允许跳级，限制回退**
- 状态可以往前跳级（如直接从跟进中变为已成交）
- 非已成交状态回退：填写原因直接回退，仅做记录
- 已成交状态回退：分两种情况，逻辑完全不同

---

**情况一：销售员主动发起状态回退（无退款）**

触发场景：客户暂缓、手误点了已成交、录入错误等，钱还没退。

```
销售员发现状态需要回退
    ↓
在 CRM 里发起回退申请 + 填写原因
    ↓
主管收到审批通知
    ↓
主管选择业绩处理方式：
  · 保留本次业绩（客户暂缓，非销售员责任）
  · 不影响业绩（录入错误场景）
    ↓
审批同意 → 状态回退，系统记录决定，留存备查
```

> 这个场景里没有发生退款，主管不需要选"追回提成"，只需要决定业绩是否保留。

---

**情况二：退款触发的状态自动变更（外部系统触发）**

触发场景：客户已付款，然后申请退款，退款由财务/客服系统发起。

```
客户申请退款
    ↓
财务/客服系统完成退款操作
    ↓
退款信息自动同步到 CRM
CRM 系统自动将客户状态从"已成交"变更
    ↓
系统同时自动预警通知销售员和主管
    ↓
主管查看退款原因，标记提成处理决定和状态变更方向
```

退款类型（决定状态变更到哪里）：
- 全额退款，客户完全放弃 → 客户状态变为「已流失」
- 全额退款，客户暂缓 → 客户状态变为「意向客户」
- 部分退款，合同继续执行 → 客户状态保持「已成交」，更新订单金额

提成处理：
- 追回全部提成
- 追回部分提成
- 不追回

> 主管一次操作，同时决定两件事：客户状态去哪里、提成怎么处理。状态变更不能由系统自动判断，因为系统不知道退款背后的真实原因。

---

**两个情况的核心区别：**

| 对比项 | 情况一（主动回退） | 情况二（退款触发） |
|--------|----------------|----------------|
| 发起方 | 销售员主动申请 | 外部系统自动触发 |
| 钱有没有退 | 没有 | 已经退了 |
| 主管处理的是 | 审批是否允许回退 | 决定提成如何处理 |
| 主管的选项 | 保留业绩 / 不影响业绩 | 追回全部 / 追回部分 / 不追回 |

### 客户核心功能

1. **客户列表**：搜索、筛选、排序，销售员只看自己负责的
2. **新建客户**：手机号实时查重，光标离开输入框立即触发
3. **客户详情页**：所有信息 + 跟进记录 + 相关订单
4. **编辑客户**：支持内联编辑高频字段
5. **归档客户**：不删除，冷冻数据，可恢复
6. **客户分配**：主管将客户转移给其他销售员

## 四、查重逻辑

### 触发时机

光标离开手机号输入框时立即查重，不等到提交。

### 查重字段优先级

| 优先级 | 字段 | 说明 |
|--------|------|------|
| 第一 | 手机号 | 最强唯一标识，完全匹配才算重复 |
| 第二 | 公司名称 + 联系人姓名 | 手机号未填时的辅助查重 |
| 第三 | 邮箱 | 唯一性强，作为补充 |

**为什么不只查手机号？**
- 同一客户可能有多个号码（手机、座机、备用机）
- 公司总机号码可能对应多个不同联系人，容易误判
- 部分线索信息不完整，手机号根本没填

### 查重结果展示

**重复的是自己的线索：**
```
⚠️ 该手机号已存在于你的线索中
线索名称：张三  创建时间：2026-01-15  来源：百度广告
[查看该线索]  [继续新建]
```

**重复的是别人的线索：**
```
⚠️ 该手机号已由 销售员A 录入
如有疑问请联系管理员处理
[我知道了]
```

### 提交策略

推荐软提示：允许提交但二次确认，提交后系统打上"疑似重复"标签，管理员后台统一处理。

**允许重复提交的风险：**
- 客户被两个销售同时跟进，体验极差，影响成交率
- 内部销售抢单纠纷，影响团队氛围
- 数据质量变差，报表数据失真
- 同一客户跟进记录分散，无法看到全貌

> 核心思路：**不让销售员自己决定，交给管理员裁决。**

### 管理员后台处理疑似重复

管理员后台有一个"疑似重复"列表：

```
疑似重复列表
─────────────────────────────────────────────
序号  手机号          记录A           记录B
001   138****8888    张三（销售员A）  张三（销售员B）
002   139****9999    腾讯科技（李四） 腾讯（王五）
─────────────────────────────────────────────
```

点进去看两条记录的完整信息对比，做出三种裁决：

**操作一：合并**

确认两条是同一个人，合并时解决四个问题：

第一，以哪条为主体（建议系统智能提示信息更完整的那条）：
```
请选择保留哪条记录为主：

线索A（销售员A）              线索B（销售员B）
创建：2026-01-15             创建：2026-02-10
来源：百度广告               来源：展会
姓名：张三        ✅          姓名：张三        ✅
手机：138xxxx     ✅          手机：138xxxx     ✅
职位：未填        ❌          职位：采购经理    ✅
邮箱：未填        ❌          邮箱：zhang@xx    ✅

💡 建议以线索B为主体，信息更完整

[以线索A为主体]    [以线索B为主体]
```

第二，客户归属谁：
```
合并后负责人：
● 继承主记录负责人（销售员A）
○ 手动指定：___________
```

第三，跟进记录怎么处理：两边的跟进记录全部按时间顺序合并，一条都不丢：
```
合并前：
  线索A：1月1日 电话沟通 / 1月5日 发送资料
  线索B：1月3日 微信联系 / 1月7日 约好见面

合并后：
  1月1日 电话沟通（来自线索A）
  1月3日 微信联系（来自线索B）
  1月5日 发送资料（来自线索A）
  1月7日 约好见面（来自线索B）
```

第四，来源记录怎么处理：**两条来源记录都完整保留，不丢弃任何一条：**
```
合并后来源记录：
├── 百度广告  2026-01-15  （来自线索A）
└── 展会      2026-02-10  （来自线索B）
```

这是为后续报表的渠道归因分析保留原始数据。来源标签是系统在合并时自动合并的，不需要主管手动填写。

被合并的那条记录：标记为"已合并"留存备查，不出现在日常列表里，不是真删除。

---

**操作二：删除**

确认其中一条是完全错误的数据，直接废弃。

```
删除前系统提示：
⚠️ 该记录有 3 条跟进记录，删除后不可恢复
是否先将跟进记录转移到另一条？
[转移后删除]    [直接删除]    [取消]
```

---

**操作三：忽略**

确认两条记录不是同一个人，移除"疑似重复"标签，后续不再提示。

忽略后两条记录都正常保留。如果管理员判断失误，可以在"已忽略"列表里找回重新处理。

---

**三种操作总结：**

| 操作 | 适用场景 | 数据结果 |
|------|---------|---------|
| 合并 | 确认是同一个人，两条都有有效信息 | 合成一条，跟进记录+来源记录全部保留 |
| 删除 | 其中一条是完全错误的数据 | 删掉错误记录，保留正确记录 |
| 忽略 | 同号码但确实是不同的人 | 两条都保留，移除重复标签 |

### 合并后通知两位销售员

主管合并完成后，系统同时通知两位销售员，措辞要得当：

**通知获得客户的销售员A：**
```
张三已确认归你负责，来源记录已更新：
├── 百度广告  2026-01-15
└── 展会      2026-02-10
```

**通知未获得客户的销售员B：**
```
你录入的张三，经主管确认归销售员A负责跟进。
你的跟进记录已合并至该客户，感谢你的录入。
```

**通知措辞的两个细节：**
- 肯定销售员B的贡献，让他知道录入的数据被保留了，不是白做了
- 责任在主管不在销售员A，避免两人之间产生矛盾

```
❌  差："张三已被分配给销售员A"
✅  好："经主管确认，张三由销售员A负责跟进"
```

**如果销售员B在合并前已有跟进记录：**

通知里要说清楚：
```
你对张三的2条跟进记录已合并至该客户，销售员A可以看到。
```

让销售员B知道自己的工作没有白费，也让他清楚隐私边界。

## 五、客户详情页

### 设计目标

让销售员在 30 秒内掌握这个客户的全部关键信息。

### 整体布局

```
┌─────────────────────────────────────────┐
│  顶部：客户核心信息 + 操作按钮           │
├────────────────┬────────────────────────┤
│   左侧：        │   右侧：               │
│   静态信息区    │   动态信息区            │
│                │                        │
│   基本信息     │   Tab1：跟进记录        │
│   联系人列表   │   Tab2：相关商机        │
│   自定义字段   │   Tab3：相关订单        │
└────────────────┴────────────────────────┘
```

### 设计原则

| 原则 | 说明 |
|------|------|
| 信息分层 | 核心信息在顶部，详细在左，动态在右 |
| 分块展示 | 每类信息独立成块，有标题，可折叠 |
| 操作优先 | 高频操作按钮始终显眼 |
| 空状态引导 | 没有数据时引导用户填写 |
| 操作留痕 | 所有改动有记录，可追溯 |
| 内联编辑 | 高频字段直接点击编辑，无需进入编辑模式 |

### 数据录入说明

**必须人工填写的（系统拿不到）：**
- 客户真实需求、沟通内容、客户态度和意向判断

**可以自动获取的：**
- 创建时间、操作日志（系统自动）
- 邮件往来、通话记录（绑定对应系统后自动同步）

**AI 辅助录入的方向：**

| 功能 | 说明 | 实现难度 |
|------|------|---------|
| 通话自动转写+总结 | 通话结束自动生成跟进记录草稿 | 低 |
| 名片识别 | 拍名片自动填入联系人字段 | 低 |
| 企业信息自动补全 | 输入公司名自动拉取工商数据 | 低 |
| 语音录入跟进记录 | 说话自动转为结构化跟进记录 | 低 |
| 合同文件识别 | 上传合同自动识别关键字段 | 中 |
| 智能跟进建议 | 分析历史记录，主动提醒销售员 | 中 |
| 微信聊天记录同步 | 授权后自动同步微信沟通内容 | 高 |

> 新一代 CRM 核心理念：**系统服务销售员**，能自动的全部自动，必须人填的尽量简单。

### 订单关联方式

**方式一：从商机转化自动生成**
```
商机谈判成功 → 点击"标记成交" → 订单自动生成并关联客户
```

**方式二：在客户下直接创建**
```
客户详情页 → 点击"创建订单" → 填写信息 → 自动关联
```

## 六、归档机制

### 什么是归档？

把数据从"活跃状态"移到"冷冻状态"，不出现在日常视图里，但数据完整保留，可随时恢复。

> 归档 = 手机"隐藏相册"：平时看不到，但还在，需要时能找回来。

### 为什么是归档而不是删除？

| 风险 | 说明 |
|------|------|
| 误删 | 销售员手滑删了重要客户，找不回来 |
| 纠纷 | 客户投诉，沟通记录已删，无法举证 |
| 数据关联断裂 | 客户删了，相关订单、跟进记录出现孤岛 |
| 监管合规 | 某些行业要求客户数据保留一定年限 |

### 触发归档的场景

| 场景 | 说明 |
|------|------|
| 客户明确拒绝 | 永远不会购买 |
| 客户长期失联 | 多次联系无响应 |
| 重复数据清理 | 管理员处理重复线索 |
| 客户公司注销 | 客户主体不存在了 |
| 历史数据整理 | 批量归档老数据 |

### 归档对各场景的影响

| 场景 | 归档后表现 |
|------|----------|
| 客户列表 | 默认不显示 |
| 筛选条件 | 默认不显示，可勾选"包含已归档"显示 |
| 数据报表 | 历史数据正常统计，标注已归档 |
| 查重 | 仍然参与查重 |
| 新增跟进/分配 | ❌ 不能操作 |

### 归档状态流转

```
正常客户 → 手动归档（填写原因）→ 已归档 → 申请恢复（管理员审批）→ 正常客户
```

**设计要点：**
- 归档时必须填写原因（客户明确拒绝 / 长期失联 / 重复数据 / 其他）
- 归档按钮放在"更多操作"里，不要太显眼，防止误操作
- 归档原因是有价值的数据，可用于分析客户流失原因

## 七、客户分配（转移）

### 触发转移的场景

| 场景 | 说明 |
|------|------|
| 销售员离职 | 最常见，客户需要交接 |
| 客户级别提升 | 换更有经验的销售接手 |
| 区域调整 | 销售区域重新划分 |
| 销售能力不匹配 | 主管判断需要换人 |
| 客户主动要求 | 客户不想跟这个销售合作 |

### 转移后的完整流程

```
主管发起转移 + 填写原因
    ↓
系统同时通知原销售员和新销售员
    ↓
原销售员失去访问权限
新销售员获得访问权限
    ↓
客户详情页自动生成操作日志
```

**通知措辞要得当：**
```
❌ 差："你的客户腾讯已被转移"
✅ 好："腾讯科技已完成交接，负责人已调整为李四，感谢你前期的跟进工作"
```

### 转移后权限变更

| 操作 | 原销售员 | 新销售员 |
|------|---------|---------|
| 查看客户详情 | ❌ | ✅ |
| 查看跟进记录 | ❌ | ✅ |
| 新增跟进记录 | ❌ | ✅ |
| 查看个人历史业绩 | ✅ | ✅ |

### 业绩分配

转移时主管需要声明业绩归属：

```
业绩分配方式：
○ 全部归新销售员
○ 全部归原销售员
○ 按比例分配：原销售员 ___% / 新销售员 ___%
```

> 必须在转移时当下固定，事后补记会引发争议。

## 八、退款处理流程

### 退款来源

退款由财务/客服系统发起，自动同步到 CRM，不是销售员在 CRM 里操作的。

### 通知角色与职责

| 角色 | 收到通知 | 职责 |
|------|---------|------|
| 负责销售员 | ✅ 主管处理完后通知 | 了解退款原因，跟进挽回客户 |
| 销售主管 | ✅ 第一时间 | 判断原因，标记提成处理决定 |
| 财务/管理层 | ✅ 大额退款触发 | 超过阈值金额时自动通知 |

> 先让主管处理完，再把结果通知销售员，避免销售员等待期间产生焦虑和抵触情绪。

### 提成节点与退款影响

| 提成节点 | 退款影响 |
|---------|---------|
| 以签单为节点 | 退款后需要追回提成，麻烦 |
| 以回款为节点 | 付款前退款不影响；付款后提成已发则需追回 |
| 以回款比例为节点 | 最精准，但计算最复杂 |

> 建议以**回款为节点**计算提成，是最常见的成熟做法。

### 通知方式建议

| 层级 | 方式 | 适合场景 |
|------|------|---------|
| 站内通知 | 系统内消息列表 | 普通提醒 |
| 短信/邮件 | 发到手机或邮箱 | 重要事项 |
| 企业微信/钉钉 | 即时推送 | 退款这类紧急事项 |

## 十、权限体系

### 两个维度

```
权限
├── 数据权限（能看谁的数据）
└── 功能权限（能做什么操作）
```

### 数据权限

| 角色 | 数据范围 |
|------|---------|
| 销售员 | 只看自己负责的数据 |
| 销售主管 | 看本部门所有人的数据 |
| 总监 | 看所有部门的数据 |
| 超级管理员 | 全公司所有数据 |

### 功能权限

| 功能 | 销售员 | 销售主管 | 管理员 |
|------|--------|---------|--------|
| 新建客户 | ✅ | ✅ | ✅ |
| 编辑自己的客户 | ✅ | ✅ | ✅ |
| 删除客户 | ❌ | ❌ | ✅ |
| 归档客户 | ✅ | ✅ | ✅ |
| 转移客户 | ❌ | ✅ | ✅ |
| 导出数据 | ❌ | ⚠️ 仅本部门+审批 | ✅ |
| 查看报表 | ⚠️ 仅个人 | ⚠️ 仅本部门 | ✅ |
| 修改系统设置 | ❌ | ❌ | ✅ |
| 审批状态回退 | ❌ | ✅ | ✅ |
| 标记退款处理决定 | ❌ | ✅ | ✅ |
| 修改来源记录 | ❌ | ✅ | ✅ |

> 来源记录只有主管才能修改，销售员只能查看，防止因归属纠纷导致数据被篡改。

### 协作者机制

在不改变客户归属的前提下，允许特定人员访问某个客户的数据。

**适用场景：** 大客户需要多部门协同，如商务+技术+售前共同跟进同一客户。

**协作者 vs 负责人：**

| 对比项 | 负责人 | 协作者 |
|--------|--------|--------|
| 客户归属 | 归他 | 不归他 |
| 业绩归属 | 归他 | 不归他 |
| 查看数据 | ✅ | ✅ |
| 新增跟进记录 | ✅ | ✅ 或 ❌（看配置） |
| 编辑客户信息 | ✅ | ❌ |
| 转移/归档客户 | ❌ 主管才能 | ❌ |

> 协作者机制是中期功能，初期可以先不做，用主管临时授权代替。

## 十一、功能优先级

功能优先级用于确定客户管理模块的开发顺序，避免一开始把所有功能都做重。优先保证销售能录入、跟进、查重、转化客户，主管能处理关键数据问题，其他增强能力可以分阶段上线。

### P0：必须先做

| 功能 | 说明 | 原因 |
|------|------|------|
| 线索录入 | 支持手动新建线索，填写基础信息、来源、负责人 | 没有线索录入，后续客户管理无法开始 |
| 手机号实时查重 | 新建线索 / 客户时，手机号光标离开立即查重 | 防止重复录入和销售抢单 |
| 线索转化客户 | 将有效线索转为客户，并生成联系人 | CRM 的核心流转路径 |
| 客户列表 | 支持搜索、筛选、排序，销售员只看自己的客户 | 销售日常使用频率最高 |
| 客户详情页 | 展示客户信息、联系人、跟进记录、相关订单 | 让销售能完整了解客户上下文 |
| 客户级别 | 支持 A / B / C 类客户标记，列表可按级别排序 | 帮助销售优先跟进高价值客户 |
| 基础权限 | 区分销售员、销售主管、管理员的数据范围和操作权限 | 防止越权查看和误操作 |

### P1：第二阶段做

| 功能 | 说明 | 原因 |
|------|------|------|
| 疑似重复处理 | 管理员后台统一处理重复线索 / 客户 | 提升数据质量，减少人工沟通成本 |
| 客户分配 / 转移 | 主管将客户转移给其他销售员，并保留转移记录 | 适配人员变动和客户重新分配 |
| 客户归档 | 不删除客户，只归档并支持恢复 | 保护历史数据，降低误删风险 |
| 客户状态回退审批 | 已成交客户申请回退时，由主管审批 | 避免销售随意调整业绩相关状态 |
| 客户级别判断模型 | 使用 BANT 模型根据预算、决策权、需求、时间自动建议 A / B / C 类 | 让客户级别从主观标记升级为可解释判断 |
| 来源记录权限 | 销售员查看，主管可修改来源记录 | 防止归属争议引发数据篡改 |
| 退款处理通知 | 退款后通知销售、主管、财务处理状态和提成 | 保证退款场景闭环 |

### P2：后续增强

| 功能 | 说明 | 原因 |
|------|------|------|
| 协作者机制 | 在不改变客户归属的前提下，授权其他人协同查看 / 跟进 | 适用于大客户和跨部门协作 |
| 来源配置后台 | 管理员维护来源大类、小类、启用 / 停用状态 | 适配渠道变化 |
| 批量导入线索 | 支持 Excel 批量导入并执行查重 | 提升线下活动、渠道名单导入效率 |
| 导出审批 | 销售主管导出本部门数据时需要审批 | 降低客户数据外泄风险 |
| 智能合并建议 | 系统根据手机号、公司名、邮箱推荐主记录 | 提升管理员处理重复数据效率 |
| SCOTSMAN 深度评估 | 在意向客户 / 谈判中阶段，用更细维度评估大客户价值 | 适用于大客户销售和复杂成交场景 |

### 暂不建议初期做

| 功能 | 暂缓原因 |
|------|----------|
| 复杂自动归因模型 | 初期数据量和来源质量不足，容易算错归属 |
| 过细的字段权限 | 会显著增加配置复杂度，先按角色控制即可 |
| 全自动客户状态判断 | 退款、流失、暂缓等状态依赖业务判断，不能完全交给系统 |
| 复杂销售协同流程 | 初期先用负责人 + 主管授权解决，等业务稳定后再抽象 |

> 优先级原则：**先保证核心业务闭环，再处理数据治理，最后做效率提升。**

## 十二、核心设计原则总结

1. **历史数据永远不能因为配置变更而丢失或变空**
2. **数据只归档，不删除**（删除权限仅超级管理员）
3. **查重必须跨全库查，但不暴露他人数据详情**
4. **所有关键操作必须留痕，可追溯**
5. **高风险操作需要审批，低风险操作填原因即可**
6. **初期做窄边界，功能稳定后再扩展**
7. **系统服务销售员，能自动的全部自动，必须人填的尽量简单**
8. **来源记录收集和归因计算分开——收集时不丢弃任何来源，归因方式在报表里决定**
