# HARNESS（product_ai_tool）

本文档定义 **AI Demo 标注工具** 多 Agent 协作开发的全局约束。  
它不是某一个 Agent 的职责说明，而是主控 Agent 与所有子 Agent 都必须遵守的统一执行边界。

补充：关于防重复、返工上限、幂等处理、长流程兜底与升级机制，统一以 [EXECUTION_POLICY.md](./EXECUTION_POLICY.md) 为准。

## 1. 目标

Harness 用来保证多 Agent 协作时：

- 不偏离已确认需求
- 不跳过必要阶段
- 不出现多个角色各自改一套口径
- 不在缺少证据时回写进度
- 不把讨论中的结论当成冻结结论执行

## 2. 权威来源优先级

发生冲突时，按以下顺序处理：

1. 用户当前明确指令
2. [产品功能开发.md](./产品功能开发.md)
3. [progress.md](./progress.md)
4. [AGENTS.md](./AGENTS.md)
5. [agents/](/Users/linfeng/Desktop/project/product_ai_tool/agents) 下各角色文档
6. 各轮产物文档（`outputs/...`）

规则：

- 下位文档不得覆盖上位文档
- 若下位文档与上位文档冲突，必须升级给主控 Agent 或负责人处理
- 未确认的新结论，不得直接写回权威文档

## 3. 角色共同行为约束

- 所有 Agent 开工前都要先读取本轮所需的上游文档
- 所有 Agent 只能在自己的职责边界内输出结论
- 不允许跳过产品、设计、架构直接进入开发，除非负责人明确授权
- 不允许用修改需求文档的方式掩盖实现缺口或测试缺口
- 不允许把标注数据写入 AI 生成的 Demo HTML
- 不允许在没有证据的情况下声称某项已完成

## 4. 交接约束

- 每次交接必须明确：本轮目标、关联 `progress` 序号、产物路径、风险项、建议勾选项
- 上游输出不完整时，下游 Agent 应拒绝继续推进，并反馈缺失项
- 主控 Agent 负责判定交接是否成立；子 Agent 不自行宣布进入下一阶段

## 5. 进度回写约束

- 默认只有主控 Agent / 负责人可以更新 [progress.md](./progress.md)
- 产品、设计、架构、开发、测试只提交「建议勾选 + 证据」
- 没有测试结论的“开发完成”不能等价为“该功能已完成”
- `progress.md` 中每个功能点建议同时记录产物或证据链接

## 6. 变更控制约束

- 任何超出 MVP 范围的内容都必须先标记为“新增需求”或“下一阶段候选”
- 涉及以下事项时，必须暂停并等待确认：
  - 需求范围变化
  - 数据模型变化
  - 接口契约变化
  - 安全策略变化
  - 版本策略变化

## 7. 并行与冲突约束

- 多个 Agent 可以并行分析，但不能并行输出互相冲突的冻结结论
- 多个 Agent 不应同时修改同一份核心文档，除非由主控 Agent 串行编排
- 如果不同角色对同一问题给出冲突结论，由主控 Agent 汇总后升级处理

## 8. 验收约束

- 验收以需求文档、设计规范、架构规范、`progress.md` 为依据
- 测试 Agent 有权对不满足验收标准的交付打回
- “可运行”不等于“可验收”；“演示通过”不等于“测试通过”

## 9. 项目特定硬约束

- Demo 必须是单 HTML
- 标注层必须与 Demo HTML 分离
- 页面识别依赖 `pageKey`
- 页面切换依赖 `postMessage`
- MVP 默认只支持单条标注驱动修改
- 重新生成 Demo 时必须考虑已有标注错位风险

## 10. 主控 Agent 的 Harness 职责

主控 Agent 除了做流程编排，还必须执行以下 Harness 检查：

- 检查本轮目标是否落在 MVP 范围内
- 检查上游输入是否完整
- 检查是否存在角色越权
- 检查建议勾选是否有证据支撑
- 检查是否满足回写 `progress.md` 的条件

## 11. 完成信号

当某轮迭代满足以下条件时，才可视为闭环：

- 产品、设计、架构、开发、测试链路已走通
- 已有对应产物
- 已有测试结论
- `progress.md` 已由主控 Agent / 负责人统一回写
